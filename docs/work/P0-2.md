## 1. 目标与边界

### 目标

把已导入 JD 按 P0-1 数据合同转换为可持久化、可追溯、可评测的结构化抽取结果，对结构或证据错误进行有限重试和明确记录。

### 非目标

- 不在本功能内优化原子粒度指标或跨 JD 归并。
- 不开发复杂前端、业务 API 或自动爬取。

### 验收标准

1. 真实 JD 可按统一数据合同完成模型抽取并持久化。
2. 结构错误、JSON 错误和证据不存在会触发有限重试，最终失败有明确原因。
3. 模型、Prompt、Schema 和抽取结果具有可追溯版本信息，版本间互不覆盖。
4. 小规模真实验证最终失败为 0，关键确定性路径有自动化测试。

## 2. 接口与不变量

- 使用 P0-1 正式数据合同，不在抽取阶段生成标准要求项；输出证据必须能在对应 JD 原文中定位。
- **抽取器版本** = `model_name + prompt_version + schema_version`，是抽取结果的身份；重跑不得覆盖其他版本结果。
当前唯一抽取配置：

```text
prompt = 0.8  schema = 3.0  （两段式，proficiency = unknown / basic / advanced）
```

已被淘汰的旧 Prompt（V2.3.1、v0.6、v0.7）、旧 Schema V2 与五级熟练度兼容逻辑不再维护，历史由 Git 与已有报告保存；正常 CLI、`extract_job()`、持久化和验收统一使用 v0.8 + Schema V3。旧数据库或旧抽取结果视为历史派生数据：当前流程发现旧 Schema 数据时明确拒绝并提示重新抽取。
- 有费用调用必须显式执行。

## 3. 当前实现

- `app/extraction.py`：确定性请求配置、JSON 解析、合同校验、证据校验和有限重试；`extract_job` 转发两段式流程（`app/extraction_two_stage.py` 的发现段+判断段），`PROMPT_VERSION=0.8` / `SCHEMA_VERSION=3.0`（唯一实现，与 `TWO_STAGE_PROMPT_VERSION` / `TWO_STAGE_SCHEMA_VERSION` 同步，测试锁定）。
- `app/extraction_two_stage.py`：发现段/判断段中间合同、唯一覆盖、证据校验和有限重试；当前唯一配置 v0.8 + Schema V3（无版本选择分支）；`extract_job_two_stage_with_discovery` 暴露发现段结果供验证与审计。
- `app/extraction.py`、`app/cli.py`：选择 JD、持久化成功结果、显示有限失败信息。
- `app/config.py`：LLM 配置。

## 6. 关键变更

- 原子化策略：先识别独立交付再决定合并动作、区分非穷举示例与直接点名技术（`docs/DECISIONS.md` DEC-007），语义边界规则持续有效。
- v0.6 → v0.7（历史候选）：判断段与发现段 Prompt 引用 P0-1 稳定规则 ID（RESP/REQ/GROUP/FIELD/EVID/COVER），删除针对单个历史 case 的补丁式示例，保留少量领域中性正反例。
- v0.7 → v0.8（本轮候选）：FIELD-03 熟练度收缩为三级（unknown/basic/advanced，DEC-016），JSON Schema 与 Prompt 不再出现旧五级值；熟练度变化不影响 importance、category、逻辑组和证据语义。

## 7. 当前结论

正式可用。两段式架构（discovery 全局扫描 + judge 局部判断 + 确定性代码负责合同和证据）保持不变；v0.8 + Schema V3 是唯一当前实现（正常抽取、持久化和验收统一使用）。旧 Prompt、旧 Schema V2 与五级熟练度不再维护，历史由 Git 与已有报告保存。正式质量证明采用 P0-3 的规则符合性、稳定性与鲁棒性验证（DEC-015）；真实 Pilot / Acceptance 尚未执行，不得宣称 v0.8 已通过真实验收。
