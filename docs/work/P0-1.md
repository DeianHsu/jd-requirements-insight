## 1. 目标与边界

### 目标

建立可供抽取、持久化和评测共同使用的数据合同与语义决策规则：人类定义数据合同、语义规则、合法判断空间、风险边界和审计方法；LLM 根据具体 JD 自主完成职责边界、要求原子化、字段和逻辑关系判断；确定性代码负责 Schema、证据、覆盖、唯一性、版本、重试和持久化。

### 非目标

- 不负责真实模型抽取质量、Prompt 优化或跨 JD 要求归并。
- 不预置具体领域技能词表，不把标准要求项混入抽取 Schema。
- 不再以人工完整 JSON 答案作为唯一正确输出，不以人工答案 F1 或期望数量作为正式 Prompt 验收门槛（DEC-015）。

### 验收标准

1. 数据合同覆盖职责、要求、类型、重要程度、经验、学历、岗位级别和证据边界；熟练度采用 Schema V3 三级枚举（unknown/basic/advanced，DEC-016），旧五级值读取时确定性映射。
2. 语义规则带稳定 ID（`RESP-*`、`REQ-*`、`GROUP-*`、`FIELD-*`、`EVID-*`、`COVER-*`），可被 Prompt、测试和审计报告引用；人工按规则审计违规而不是对照唯一答案。
3. Schema、数据库模型和规则语义一致，旧库迁移可重复执行且不丢失数据。
4. 关键校验和迁移具有确定性自动化测试；合同检查、运行间比较与规则场景检查由 `app/extraction_validation.py` 覆盖。

## 2. 接口与不变量

- 完整字段语义以 `docs/GLOSSARY.md` 和 `docs/annotation/` 为准，代码模型必须一致；新增或冲突术语先更新 GLOSSARY。
- 每项职责和要求绑定可在原文定位的连续证据；不确定内容不得臆测。
- `group_id + group_logic` 表达任选关系；经验上下限和原始表达分开保存。
- 要求实例与标准要求项分层，抽取阶段不得提前归并同义表达。
- 规则 ID 稳定且唯一；修改规则语义必须同步更新规则 ID 对应条文、Prompt 引用和测试。

## 3. 当前实现

- `app/schemas.py`：Pydantic 抽取数据合同 V2（职责、原子要求、逻辑组、年限、证据校验）。
- `app/models.py`、`app/database.py`：SQLAlchemy 持久化与可重复执行的增量迁移，保留旧数据。
- `docs/annotation/`：语义决策规则 1.5，规则带稳定 ID，按职责、要求与证据/场景协议拆分。
- `app/extraction_validation.py`：确定性合同检查、运行间比较与验收报告（P0-3 新协议）。

## 6. 关键变更

- 数据库结构 V1 → V2 采用可重复执行的增量迁移（决策记录 DEC-011），该机制仍是当前方案。
- 人工 Gold 方法、标注流程、数据集身份、评测协议和人工审计角色重新开启（DEC-015）：人工不再为每条 JD 提供唯一完整 JSON 答案，改为规则制定与违规审计；旧 `annotation_cases.json` 标记为 legacy 历史材料。
- 熟练度收缩为三级（DEC-016）：Schema V3（unknown/basic/advanced）用于 candidate v0.8；旧 V2 五级值读取时确定性映射（understand/familiar → basic、proficient/expert → advanced），物理数据不重写；`none` 属于未来候选人个人能力层，不属于岗位要求。

## 7. 当前结论

数据合同、数据库模型与迁移保持已批准（bdd8932）；语义规则与验证方法按新协议重新验收中（PARTIAL）。规则 ID 体系已建立，人工角色已迁移为规则制定与违规审计，旧人工标注降级为 legacy 历史材料。当前正式抽取版本仍是两段式 v0.6（`approved under legacy Gold protocol`），直至新协议完成验收。
