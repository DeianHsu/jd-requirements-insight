# JD Skill Insight 全项目术语词典

本文是项目术语含义的唯一信息源。代码、测试、计划、决策、README和handoff必须使用下列标准术语；发现新术语、同词异义或定义冲突时先更新本文，再同步受影响内容。

事实来源按“已提交代码合同与自动化测试 → 生效中的决策记录 → 当前文档”排序。仅存在于未提交开发草稿中的类名、字段或枚举不是稳定合同，不得据此宣称功能已经实现或术语已经定案。

## 统一命名规则

1. 中文正文使用本词典规定的唯一中文标准术语，不为同一对象交替创造简称、译名或近义名称。
2. 类名、字段名、枚举值、文件名和CLI命令保留准确的英文代码标识符，并使用反引号；代码标识符不构成另一套业务术语。
3. 一个标准术语只表示一个业务对象；不同业务对象不得共用同一名称。
4. 名称必须匹配实际业务范围：只在明确表示技术能力时使用“技能”，不使用范围过大的“概念”代替岗位要求。
5. 新增公共类、枚举、CLI、标题或业务名称前必须检查本词典；确需新增时先确定中文标准术语及对应代码标识符。
6. 历史文档中的旧称应同步改为当前标准术语；只保留历史工程事实、指标和版本，不保留会误导后续开发的过时名称。
7. 术语继续按业务类别和处理顺序组织，不按字典序重排。

## 数据生命周期与抽取单位

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| JD | 一份岗位描述，是正式结构化抽取、持久化和后续统计的来源单位 | 一个困难样例或一条岗位要求 |
| 已解析JD | `JobDocument`表示的、已从Markdown正文和Front Matter解析并通过输入校验、但尚未持久化的JD | 数据库记录或抽取结果 |
| 已持久化JD | `JobDescription`表示的JD数据库记录，保存来源、招聘元数据、原文和内容哈希 | 结构化抽取结果 |
| 内容哈希 | 对JD正文执行Unicode NFKC与空白规范化后计算的SHA-256，用作内容级去重标识；规范化只作用于哈希输入 | 修改数据库中的JD原文，或按文件名去重 |
| 文本规范化 | 为哈希、证据包含或确定性名称比较而执行的Unicode、大小写、空白或标点处理；必须说明具体用途 | 同义判断、要求归并或要求映射 |
| 幂等 | 对同一业务身份重复执行不会新增重复记录；JD导入按内容哈希判断，抽取结果按JD与抽取器版本判断 | 每次都重新调用模型，或所有命令都没有副作用 |
| 批量导入 | 一次`import-jds`调用扫描的Markdown文件及其发现、成功、跳过和失败汇总；每个文件使用独立数据库事务 | 可跨运行引用的业务实体 |
| 结构化抽取 | P0-2以一份完整JD为输入，按抽取数据合同输出岗位方向、岗位级别、职责和原子要求，并执行结构与证据校验 | 跨JD要求归并、统计或完整分析运行 |
| 抽取结果 | 一个抽取器版本针对一份JD产生并通过校验的`JobExtractionResult`及其`JobExtraction`持久化记录 | 抽取批次、要求归并结果或运行日志 |
| 抽取器版本 | `model_name + prompt_version + schema_version`组成的抽取结果身份，用于幂等保存和版本比较 | 单独的Prompt版本、数据库结构版本或一次运行ID |
| 批量抽取 | 一次`extract-jds`调用选择的若干JD及其发现、成功、跳过和失败汇总 | 可跨运行引用的业务实体 |
| 职责 | 入职后需要完成的一项可独立描述或验收的工作；`ResponsibilityItem`保存名称和证据 | 候选人需要具备的条件 |
| 岗位要求 | 公司对候选人的一项技能、经验、学历、专业、行业知识或软能力条件 | 只表示技术技能，或岗位职责本身 |
| 原子要求 | 按原子化规则表达的一条`RequirementItem`，只包含一个可独立学习、分类、评价、匹配或统计的条件；固定复合要求可以整体保留 | 必须压缩成单个技术词，或跨JD共享的标准要求项 |
| 固定复合要求 | 已形成稳定整体含义，或拆分后会改变招聘条件原意的复合表达，例如“数据结构与算法”；是否整体保留按原子化规则判断 | 任意包含“和”“与”或顿号的长要求 |
| 要求实例 | 某份JD、某个抽取结果中的一条具体原子要求，带原始名称、属性、逻辑组、年限、证据和置信度 | 跨JD共享的标准要求项 |

## 抽取数据合同、字段与枚举

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| 抽取数据合同 | `JobExtractionResult`及其Pydantic子模型定义的模型输出结构和业务校验规则；当前稳定版本为V2 | SQLAlchemy表结构或SQLite迁移 |
| 数据库结构 | SQLAlchemy模型、表、字段、外键、索引、唯一约束和迁移规则 | LLM输出JSON合同 |
| 岗位方向 | `RoleFamily`限定的岗位业务方向：`agent_application`、`llm_application`、`rag_application`、`ai_algorithm`、`ai_platform`、`other`、`unknown` | 岗位级别或要求类别 |
| 岗位级别 | `Seniority`限定的市场级别：`junior`、`transition`、`mid`、`senior`、`unknown` | 经验年限的直接换算结果；不得根据工资推断 |
| 要求类别 | `RequirementCategory`限定的稳定分组维度：`programming_language`、`backend_engineering`、`agent_framework`、`agent_capability`、`rag`、`llm_application`、`model_training`、`ml_framework`、`retrieval`、`deployment`、`software_engineering`、`domain_knowledge`、`education`、`experience`、`soft_skill`、`other` | 标准要求项或要求关系 |
| 重要程度 | JD对岗位要求是否构成硬性条件或偏好的表达：`must`、`preferred`、`mentioned`、`unknown` | 熟练度或模型置信度 |
| 熟练度 | JD明确表达的掌握程度：`understand`、`familiar`、`proficient`、`expert`、`unknown` | 工作年限、项目经验或模型置信度；不得由“有经验”自动推断 |
| 要求逻辑组 | 用`group_id + group_logic`保留原句的组合逻辑；`standalone`是独立条件且不得有`group_id`，`any_of`是至少两个共享非空`group_id`的任选成员 | 要求归并或同义映射 |
| 经验年限范围 | `min_years`保存最低门槛，`max_years`只保存原文明示上限，`years_text`保存完整原文表达 | 由岗位级别或常识推断的年限 |
| 证据 | JD原文中连续出现、能够支持职责或岗位要求及其字段判断的最小充分文本 | LLM改写、跨段拼接、映射理由或要求关系依据 |
| 抽取置信度 | `RequirementItem.confidence`中0到1的抽取置信度；人工标准答案按标注规范使用`1.0` | 证据支持性已经自动证明，或要求映射置信度 |
| `unknown` | 稳定枚举中表示原文不足以判断的显式值 | 缺失字段、`null`或任意错误兜底 |
| `null` | 抽取数据合同允许字段缺省时使用的空值 | 可用`unknown`表达的“无法判断” |

字段的完整标注规则和示例以[标注规范索引](annotation/README.md)为准；词典只固定跨模块名称与边界。

## 人工标准答案、困难样例与评测

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| 人工标准答案 | 经人工确认并冻结的期望结果；完整JD的人工标准答案由`GoldenExtractionRecord`绑定来源文件与期望抽取结果，用于校验和评测 | 正常业务运行逐条人工审核全部数据 |
| 困难样例 | 从真实JD中选出的一个困难句子评测单元，包含人工期望的职责或岗位要求列表；数据文件中仍使用`case`相关字段名 | 正式抽取单位、单个技能、整份JD或完整JD人工标准答案 |
| 评测 | 将指定模型、Prompt和抽取数据合同版本的结果与人工标准答案或困难样例对比，分层报告发现、原子化、字段、逻辑组、年限和证据质量 | 用单一总分代表系统质量 |
| 开发集 | 已用于调整Prompt、抽取数据合同或规则的样例分组；代码值为`development` | 未见验证集 |
| 回归集 | 已经暴露给设计或调参过程、保留下来检查已知能力是否回退的样例分组；代码值为`regression` | 可以继续宣称为未见验证集 |
| 验证集 | 按预先规则选择并经人工批准冻结、用于报告泛化结果的未见样例；代码值为`validation`。一旦据其错误调参，该批数据不再承担下一轮正式验证职责 | 临时草案或开发集改名 |
| 名称代理指标 | 困难样例先用证据定位句内输出，再以保留专有英文技术词边界的确定性名称相似度做一对一匹配所得的Precision、Recall和F1 | 人工语义复核、要求映射准确率或证据支持性判断 |
| 原子项数量一致 | 一个困难样例中预测原子项数与期望原子项数完全相同 | 名称、字段和证据均正确 |
| 字段准确率 | 已匹配项目中要求类别、重要程度、熟练度、年限或`any_of`组等目标字段正确的比例 | 未匹配项目也已正确处理 |
| 证据存在性 | 单条证据经允许的文本规范化后可在对应JD原文中找到 | 证据足以支持结论或边界最小 |
| 证据存在率 | 通过证据存在性检查的项目数占适用项目总数的比例 | 证据支持率 |
| 证据支持性 | 单条证据确实足以支持抽取名称和字段判断；证据最小性作为同一人工复核中的边界要求 | 自动字符串包含检查 |
| 证据支持率 | 经人工复核为能够支持结论的项目数占被复核项目总数的比例 | 证据存在率或当前已实现的自动指标 |
| `N/A` | 指标没有适用样本，分母不存在 | 0%或评测失败 |

## 要求归并与统计

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| 跨JD原子要求归并与映射 | P0-4汇总选定范围内的全部要求实例，收敛跨JD统计口径，并为每条实例保存可追溯映射 | 合并岗位职责、删除原始要求或在抽取阶段改写`raw_name` |
| 要求归并 | 结合原始名称和证据上下文，把指向同一招聘条件的多个要求实例归并到同一标准要求项；减少的是统计口径，不是来源记录 | 字符串去重、删除要求实例或合并不同招聘门槛 |
| 标准要求项 | 多个语义相同的要求实例共同指向的跨JD统计口径；可以表示技能、经验、学历、专业、行业知识或软能力 | 覆盖或删除原始要求实例 |
| 要求映射 | 要求实例到标准要求项的可追溯关联，保存处理状态、映射理由和置信度 | 修改`raw_name`、抽取属性或原始证据 |
| 归并器版本 | `model_name + prompt_version + schema_version`组成的归并结果身份，用于按范围键幂等保存和版本比较 | 单独的Prompt版本、数据库结构版本或一次运行ID |
| 同一要求 | 表面名称不同但结合证据上下文后指向同一招聘条件；例如明确语境中的缩写、中英文名称和同义表达 | 上下位、组成或仅相关关系 |
| `is_a` | source是target的下位要求；方向固定为下位项指向上位项 | 同义归并或无方向关系 |
| `part_of` | source是target的组成部分；方向固定为组成部分指向整体 | 同义归并或上下位关系 |
| `related_to` | 两个标准要求项存在统计或业务相关性，但既不同义，也不满足明确上下位或组成关系 | 可以据此归并统计口径 |
| 映射理由 | 说明某要求实例为何映射到某标准要求项，或为何建立要求关系的结构化依据 | 原始JD证据的替代品 |
| 独立JD计数 | P0-6按标准要求项统计包含该项的不同JD数量；同一JD内多个要求实例只计一次覆盖 | 在P0-4删除同一JD内的重复要求实例 |

同一表面词可以因证据上下文不同映射到不同标准要求项。`LLM`与“大语言模型”通常可归并为同一要求；“大模型”是否相同必须依据所在要求和证据判断，不能作为全局硬编码别名。

## 项目范围、状态与验证

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| MVP | 当前求职作品版的最小可信闭环，以项目计划列出的范围和验收标准为准 | 完整招聘产品、自动投递Agent或所有长期功能 |
| P0-N | `docs/PROJECT_PLAN.md`中P0核心闭环的第N个编号功能点；例如P0-4是“跨JD原子要求归并与映射” | 通用缺陷优先级标签，或仅凭编号宣称功能已完成 |
| 阶段 | 默认对应一个可独立验收的计划功能点；大型功能可拆成可独立验收的子阶段 | 每次普通文档修改或缺陷修复 |
| 开发草稿 | 工作树中尚未提交、尚未按阶段验收的候选实现、测试或文档；可用于发现待定术语和冲突 | 既有稳定事实、已实现能力或最终数据合同 |
| 稳定合同 | 已提交代码中的公共抽取数据合同、枚举和接口，并由自动化测试确认的行为约束 | 未提交草稿中的类名、字段、枚举或README描述 |
| 小规模验证 | 静态检查通过后，使用少量测试、困难样例或数据验证本次变化 | 全量回归或业务验收完成 |
| 全量回归 | 小规模验证通过后，按影响范围执行完整测试和必要的真实数据回归 | 回归集，或昂贵调用前的随意试跑 |
| 版本确认 | 全量回归达到项目计划已有验收标准后，确认版本或标记完成 | 代码草稿存在、测试骨架通过或提交尚未产生时的完成声明 |

## 运行与公共CLI

| 标准术语 | 固定含义 | 不表示 |
|---|---|---|
| 运行日志 | 项目投入使用后，由普通日志系统在用户执行流程时追加的本地文本记录，包含时间、阶段、状态、数量、耗时和有限错误摘要 | 业务数据表、结果快照、要求映射依据或`run_id` |
| 命令行接口 | 由Typer提供的本地业务入口，用于导入、查看、抽取和评测 | 完整前端、业务API或Agent框架 |
| `import-jds` | 批量解析、校验并按内容哈希幂等导入指定目录中的Markdown JD | 结构化抽取 |
| `list-jds` | 列出已导入JD的摘要，不输出完整正文 | 导出JD数据 |
| `validate-golden` | 校验完整JD人工标准答案的抽取数据合同、来源文件和证据存在性 | 运行模型评测 |
| `extract-jds` | 对默认小批量、指定`--job-id`或显式`--all`的JD执行结构化抽取并按抽取器版本幂等保存 | 要求归并或统计 |
| `consolidate-requirements` | 对选定`--job-id`或全部JD的要求实例执行跨JD原子要求归并，按范围键与归并器版本幂等保存标准要求项、要求映射和关系 | 抽取或统计 |
| `list-consolidations` | 列出已持久化归并批次的归并器版本、范围、实例数及标准项/映射/关系数量摘要 | 输出完整映射、标准要求项明细或模型JSON |
| `list-extractions` | 列出已持久化抽取结果的抽取器版本、岗位方向、岗位级别及职责/岗位要求数量 | 输出完整模型JSON |
| `evaluate-extractions` | 将数据库中每份JD的最新抽取结果与完整JD人工标准答案对比 | 困难样例分层评测 |
| `evaluate-cases` | 按模型、Prompt、抽取数据合同及可选数据集分组对困难样例运行分层评测，并限制终端错误摘要数量 | 完整JD端到端质量证明 |

运行日志只用于观察程序执行情况，不参与业务关联。日志不得要求`run_id`，不得保存JD正文、完整证据、完整模型JSON、密钥或个人数据，也不得替代数据库中的抽取结果、标准要求项、映射和关系。

## 跨阶段不变量

1. P0-1定义抽取数据合同和人工标注规则，不直接产生业务数据。
2. P0-2按整份JD执行结构化抽取并产生职责和原子要求；困难样例只用于评测。
3. P0-3验证和改进原子要求的拆分粒度，不定义另一套数据类型。
4. P0-4汇总选定范围内所有`RequirementItem`对应的要求实例后统一执行要求归并与映射；职责文本中识别出的候选人条件可以进入P0-4，`ResponsibilityItem`本身不参与要求归并。
5. P0-4不得覆盖或删除`raw_name`、category、importance、proficiency、逻辑组、年限、evidence或confidence。
6. 同一标准要求项下可以保留多个来自同一JD或不同JD的要求实例。
7. 同义表达归并到同一标准要求项；`is_a`、`part_of`和`related_to`只建立关系，不触发归并。
8. P0-4代码只定义领域无关合同，不得硬编码具体领域技能；项目当前不建设独立发布版本系统。
9. P0-6才按独立JD数去重统计，P0-7通过要求映射回溯要求实例、证据和原始JD。
