## DEC-001：产品定位为岗位要求洞察，而不是简历匹配打分器

### 问题

真实求职场景中，用户需要同时阅读几十份甚至上百份 JD，很难识别高频要求、岗位差异和学习优先级。单一“匹配分”无法说明缺少什么、证据在哪里，也不能提供可靠的后续行动建议。

### 候选方案

- 简历匹配打分器：直接对简历与 JD 打分，输出单一匹配分数。
- 岗位要求洞察：先把多份非结构化 JD 转化为可统计、可追溯的岗位要求数据，再谈个人对照。

### 决策

项目首先把多份非结构化 JD 转化为可统计、可追溯的岗位要求数据，输出高频要求、必需与加分分布、要求组合和原文证据。个人简历对照与提升建议放在岗位市场数据可信之后（依赖可信岗位数据层，暂不提前开发）。

### 主要取舍

- 不把单一匹配分作为核心产品输出；
- 统计结论必须能够返回原始 JD 证据；
- 当前阶段优先建设岗位市场数据层，个人能力证据矩阵与行动建议延期。

### 结果与证据

该定位直接解决“看大量 JD 看晕”的真实问题，也展示 LLM 应用工程中的结构化抽取、质量控制、评测和数据分析能力。P0-1 至 P0-10 的全部功能清单围绕岗位数据闭环展开（`docs/PROJECT_PLAN.md`）。

### 复审条件

当岗位要求数据、要求归并和证据查询稳定后，再设计个人能力证据矩阵与行动建议。

## DEC-002：以求职作品的可信核心闭环控制 MVP 范围

### 问题

早期方案同时包含 Agent、RAG、简历匹配、学习规划、API 和前端，范围接近一个小型完整产品，容易导致每个模块都只有演示深度。

### 候选方案

- 大而全：同时建设全部模块，分阶段演示。
- 可信闭环：只建设从真实 JD 到统计报告的最小可信数据闭环，其余全部延期。

### 决策

MVP 只实现可信岗位数据闭环：5 份真实 JD 用于开发和规则验证，再按 P0-8 分阶段扩充到 15～20 份。功能顺序、样本目标和验收标准以 `docs/PROJECT_PLAN.md` 为唯一依据。

### 主要取舍

- P0 未完成前不开发 RAG 问答、LangGraph、Tool Calling 和个人匹配；
- 数据质量优先于数量；功能按风险类型和验收标准判断是否完成。

### 结果与证据

当前 5 份真实 JD 已支撑 P0-1/P0-2 验收与 P0-3/P0-4 候选开发，P0-8 正在定向扩充样本（`docs/work/P0-8.md`）。

### 复审条件

核心闭环完成并形成可演示报告后，再评估下一阶段范围。

## DEC-003：先完成数据与评测链路，不为使用框架而引入 Agent 框架

### 问题

目标岗位经常提到 LangChain、LangGraph 和 Tool Calling，但当前流程主要是确定性的“导入→抽取→校验→统计”，尚不存在必须依靠动态规划或状态图解决的问题。

### 候选方案

- 引入 LangChain/LangGraph 编排核心链路，以贴近目标岗位技术栈。
- 用 Python、Pydantic、SQLAlchemy 和明确的业务函数直接实现。

### 决策

使用 Python、Pydantic、SQLAlchemy 和明确的业务函数直接实现核心链路，不为了展示技术栈而强行加入 LangChain 或 LangGraph。

### 主要取舍

- 框架应服务真实复杂度；当前最大的工程风险是抽取粒度、证据可靠性和评测，而不是 Agent 编排；
- LangGraph 和 Tool Calling 保持延期，不是永久排除；
- 面试叙事重点是可靠 LLM 应用工程，而不是“使用过某框架”。

### 结果与证据

全部业务逻辑集中在 `app/` 的确定性模块中，实验脚本只编排正式模块（`scripts/experiments/README.md`）。

### 复审条件

出现动态条件分支、多个工具选择、长流程状态恢复或人工确认节点时，再评估 LangGraph 或其他编排框架。

## DEC-004：SQL 负责精确统计，RAG 延期用于开放式证据检索

### 问题

RAG 在目标岗位 JD 中频繁出现，具有较高求职价值，但本项目首先需要回答“多少份 JD 提到某项要求”这类精确问题。

### 候选方案

- 引入向量检索参与频率、覆盖率等统计；
- 结构化字段和 SQL 负责精确统计，RAG 延后用于开放式证据检索和解释。

### 决策

结构化字段和 SQL 负责频率、覆盖率、重要程度等精确统计；RAG 不参与计数，放到核心闭环之后用于开放式提问、相关证据召回和解释。

### 主要取舍

向量检索适合语义相关性，不适合替代可重复验证的精确统计；延后 RAG 可以避免为了技术关键词损害结果可信度，当前不安装或开发向量数据库链路。

### 结果与证据

P0-6 的统计全部基于持久化结构化数据（独立 JD 计数，见 `docs/GLOSSARY.md`），不直接统计模型长文本。

### 复审条件

当用户需要用自然语言跨 JD 查询证据，且 SQL 字段无法覆盖开放问题时实现最小 RAG 闭环。

## DEC-005：把 JD 分析定义为有证据约束的信息抽取任务

### 问题

直接让 LLM 总结 JD 会产生粒度不一致、无法统计和结论不可验证的问题。

### 候选方案

- 自由文本总结：LLM 输出自然语言摘要，人类阅读。
- 有证据约束的信息抽取：JSON Schema 约束输出、Pydantic 校验、原文证据存在性校验、有限重试、版本化持久化、人工标准答案评测。

### 决策

采用信息抽取链路：

```text
JD原文 → JSON Schema约束 → LLM抽取 → Pydantic校验 → 原文证据存在性校验
→ 有限重试 → 版本化持久化 → 人工标准答案评测
```

### 主要取舍

- 每项职责和要求必须绑定连续原文证据；不接受只有总结、没有证据的结论；
- 模型、Prompt 和抽取数据合同共同组成抽取器版本，规则变化后保留新旧结果；
- 正确性和可追溯性比语言流畅度更重要。

### 结果与证据

该原则是 P0-1 合同、P0-2 抽取、P0-5 评测和 P0-7 追溯的共同基础；正式版本 Prompt V2.3.1 在 5 份真实 JD 上 0 最终失败（`docs/work/P0-2.md`）。

### 复审条件

该原则属于项目基础约束，除非产品不再承担统计与决策支持职责，否则不取消。

## DEC-006：要求实例与标准要求项分层保存

### 问题

“LangChain 使用经验”和“有使用 LangChain 的经验”可以表达同一招聘条件；“熟悉 LangChain”或“具备 LangChain 项目经验”的门槛却不一定相同。只按表面字符串统计会导致同义表达碎片化，全部压缩成技术名“LangChain”又会丢失实践门槛。

### 候选方案

- 抽取阶段直接做同义归一，输出统一技术词；
- 抽取层保留完整原始要求（`raw_name`），归并层把语义相同的要求实例映射到标准要求项。

### 决策

P0-2 抽取层的 `raw_name` 保留完整原始要求；P0-4 把语义相同的要求实例映射到标准要求项；只共享技术对象但招聘门槛不同的要求不强制归并；原始证据和映射理由同时保留。

### 主要取舍

- 要求实例负责保留具体 JD 中的招聘门槛，标准要求项负责统一跨 JD 统计口径，两者职责不同；
- Prompt V2 禁止在抽取阶段提前做同义表达归并；
- 报告可以按标准要求项统计覆盖率，同时保留“熟悉”“使用经验”和“项目经验”等不同招聘门槛。

### 结果与证据

该分层是 P0-4 的验收合同和 `evaluate-consolidation` 评测对象（`docs/work/P0-4.md`、`docs/work/P0-5.md`）。

### 复审条件

实现跨 JD 原子要求归并与映射时复核字段名称和关系类型，但不取消分层原则。

## DEC-007：原子化的业务边界设计：统一判断标准、任选组、年限与示例

### 问题

机械按顿号、“和”或“与”拆分，会把“数据结构与算法”等固定复合要求拆坏；完全不拆又会让多个独立条件被保存成长句，无法统计。同类问题还出现在任选关系（“Python、Java、Go 中至少一种”）、年限表达（“3～5 年”）和示例表达（“至少一门主流语言（如 Go、Java 等）”）上。

### 候选方案

- 纯规则拆分：按连接词机械切分；
- 整体保留：长句不拆；
- 按业务语义边界判断：只有能够独立学习、评价、匹配和统计时才拆分，行业稳定复合表达整体保留。

### 决策

四项边界规则同时生效：

1. 一项要求只有在能够独立学习、评价、匹配和统计时才拆分；固定复合表达整体保留（完整判断步骤见 `docs/annotation/REQUIREMENTS.md`）。
2. 候选技能分别保存为原子项，用 `group_id + group_logic` 保留“任选其一”业务语义，避免把任选组误判为必须同时掌握。
3. 经验年限分别保存最低门槛、原文明示的上限和完整原始表达；默认匹配只使用最低门槛，上限不自动当作能力淘汰条件。
4. 区分非穷举示例与直接点名技术：完整上位要求后的“如/例如”或括号内容只作为示例，不建立具体技能 `any_of`；被“熟悉、掌握、使用经验”等候选条件直接修饰的具体技术名必须逐项保留，“等”只表示名单未穷尽。

### 主要取舍

- 统一规则比针对单个句子临时判断更能保证人工标准答案与模型输出粒度一致；
- 任选关系、年限和示例都保留原始语义，同时保持统计价值；
- 完整规则只在标注规范中维护，决策记录不复制示例表。

### 结果与证据

开发集要求名称/职责 F1 100%、数量一致 10/10、`any_of` 7/7（v0.6 候选门槛，`docs/work/P0-3.md`）；case_003/004/006 分别验证了示例、点名技术和不单列模型名的边界。

### 复审条件

当错误分析发现某类表达持续被漏拆或多拆时，更新规则和对应人工标准答案样例；出现“至少满足两项”等更复杂组合逻辑时，再扩展 `all_of`、`at_least_n` 等表达。

## DEC-008：使用分层评测，不用单一分数代表系统质量

### 问题

单一 F1 无法说明错误发生在漏抽、原子化、要求映射、重要程度还是证据质量；单一简历匹配分同样缺少行动指导。

### 候选方案

- 单一总分代表系统质量；
- 分层评测：抽取、原子化、要求映射、字段和证据质量分别报告，并保留错误类型与失败案例。

### 决策

抽取、原子化、要求映射、重要程度和证据质量分别评测；困难句子自动评测先用原文证据包含关系定位句内输出，再用确定性名称相似度做一对一匹配（“名称代理指标”，只用于稳定比较版本，不能替代人工语义复核）；证据最小性、职责业务粒度等主观边界继续由人工标准答案与人工错误分析判断。人工标准答案不能为了提高指标迁就模型输出。

### 主要取舍

- 分层指标能够指导下一轮修改，也能在项目展示中诚实解释系统边界；
- 名称代理指标保留 Python、LangChain 等专有英文技术词，不能把更泛的要求算作命中；
- 指标与目标值在 `docs/PROJECT_PLAN.md` 和 `docs/annotation/DATASET_EVALUATION.md` 中维护，不复制到本文。

### 结果与证据

`evaluate-cases` 已支持开发/回归/验证三个分组，`evaluate-consolidation` 报告映射准确率与关系 P/R/F1（`docs/work/P0-5.md`）。

### 复审条件

新增要求归并、统计或个人匹配模块时，为相应层增加独立指标，不把所有质量压缩成一个总分。

## DEC-009：跨 JD 原子要求由岗位语料动态归并，代码不预置领域技能

### 问题

为每个求职专业人工维护岗位要求词表和关系，会让系统随领域数量线性膨胀；在没有领域知识或语义模型的情况下，纯字符串规则无法可靠判断同义、缩写、组成、相关和上下位关系。

### 候选方案

- 人工维护领域词表 + 无 LLM 映射；
- 语料驱动：标准要求项和要求关系由 LLM 从选定范围内的要求实例及证据上下文中批量提出，确定性代码负责校验与审计。

### 决策

标准要求项和要求关系从选定范围内已抽取的要求实例及其证据上下文中，由独立的 LLM 归并阶段批量提出；应用代码只定义领域无关的输入、输出和来源合同，不硬编码具体领域技能；LLM 负责开放语义理解，确定性代码负责结构校验、冲突检测、覆盖检查和可追溯记录；项目不建设独立的归并结果发布版本系统。

### 主要取舍

- 新专业可以从自身岗位语料冷启动，不需要开发者预先编写领域要求包；
- 归并调用独立于抽取，不在抽取阶段覆盖 `raw_name` 或其他字段；
- 归并结果必须保存模型/Prompt 信息、映射理由和置信度；归并评测分别衡量同义归并、关系判断和未映射处理；
- 在归并接口与小规模人工标准答案通过前，不运行昂贵的全量要求归并。

### 结果与证据

P0-4 实现三阶段输出边界（标准项 → 分块映射 → 关系）与全局校验合同；归并判定由模型自主提出，验收口径为规则合同 + 多次运行一致性 + 人工抽样复核（DEC-012，`docs/work/P0-4.md`）。

### 复审条件

当岗位语料规模足以比较不同归并方案时，评估嵌入聚类、外部公开要求库或 LLM 与检索结合的成本和质量。

## DEC-010：归并批次身份绑定完整输入版本

### 问题

归并批次原来只按范围键和归并器版本判断幂等。新增 JD、重抽取或要求内容变化后，`all` 范围和归并器版本仍保持不变，系统会错误跳过并继续使用旧批次；按每份 JD 最大抽取记录 ID 装配还可能混用不同抽取器版本。

### 候选方案

- 只按范围键 + 归并器版本做幂等；
- 显式冻结输入版本，把输入指纹纳入批次身份。

### 决策

归并前显式冻结选定 JD、覆盖全部选定 JD 的共同抽取器版本、抽取记录和完整要求实例；对输入执行确定性序列化并计算 SHA-256 归并输入指纹；批次业务身份固定为范围键、归并器版本和归并输入指纹三者组合。CLI 必须显式选择 `--all` 或 `--job-id`，目标 JD 缺少目标抽取版本时整体失败。历史批次保留原记录，不伪装成可完整还原的新输入指纹。

### 主要取舍

- 兼顾重复执行幂等、输入变化后重新归并、历史结果共存和下游统计可复现性；
- SQLite 旧表需要保留数据地重建唯一约束；
- P0-6 必须选择明确的归并批次，不能仅凭 `scope_key=all` 推断数据最新且完整。

### 结果与证据

P0-4 已实现输入指纹批次身份与显式批次离线评测；旧批次隔离指纹用于历史结果复算（`docs/work/P0-4.md`、`docs/GLOSSARY.md`）。

### 复审条件

当归并输入规模需要分批或增量更新时，复审是否把单一输入指纹扩展为分片清单或父子批次；在此之前不引入复杂的发布版本系统。

## DEC-011：SQLite 数据库结构升级采用可重复执行的增量迁移

### 问题

数据库结构 V2 增加逻辑组和年限字段，直接修改 ORM 但不处理现有数据库会导致本地旧库无法运行；直接删除数据库又会丢失已有抽取结果。

### 候选方案

- 删除旧库重建；
- 引入 Alembic 版本化迁移；
- 可重复执行的静态 `ALTER TABLE` 增量迁移。

### 决策

初始化 SQLite 时检查缺失字段，以静态 `ALTER TABLE` 增量补列、回填旧最低年限并创建索引；迁移设计为可重复执行，不删除旧记录。

### 主要取舍

- 当前项目只有单机 SQLite，轻量迁移足以控制风险，比立即引入完整迁移基础设施更符合 MVP 规模；
- V1 数据库可继续使用，旧物理列暂时保留，抽取结果通过抽取器版本区分。

### 结果与证据

迁移逻辑位于 `app/database.py`，`tests/test_database.py` 覆盖 V1 到 V2 迁移（`docs/work/P0-1.md`）。

### 复审条件

当项目需要多人协作、生产数据库、多环境发布或更复杂结构变更时，迁移到 Alembic 版本化迁移。

## DEC-012：归并验收不设人工金标准，改为合同 + 稳定性 + 变形测试 + 下游不变性

### 问题

P0-4 归并验收原依赖一份"人工标准答案"（`data/consolidation_cases.json`），但该文件来源和审核过程无法确认，从未经用户确认冻结；模型在"大模型微调经验 part_of 大模型应用落地经验"等语义判定上与草案稳定分歧，4 轮 Prompt 调整（v1.8→v2.1）均不收敛。分歧根源是主观归类差异而非模型错误——用一套来源不明的草案卡模型，是在错误基准上优化。

### 候选方案

- 维持草案基准，换更强模型重跑预检（费用高，不保证认同草案口径）；
- 接受现状，正式验收仅如实报告未达标（放弃质量证明）；
- 调整标注口径迎合模型（测试污染风险）；
- 取消人工金标准：归并判定全由模型自主提出，开发者只负责规则与验收指标。

### 决策

归并判定（标准项、同义映射、关系）完全由模型自主提出，不设人工金标准；验收改为：P0-4A 合同与完整覆盖（100%）+ 变形测试（输入顺序/分块大小不变性、精确重复、保守回退、无关输入隔离）+ 3 次独立运行稳定性（co-clustering agreement）+ P0-4B 图合同（broader_than 唯一、无环无冲突）+ 关系图稀疏度 + 下游统计不变性 + 人工抽样审计；全部指标分级为 hard gate / warning / diagnostic，输出机器可读验收报告。来源不明旧夹具已删除，不再作为项目资产（DEC-013）。

### 主要取舍

- 人工角色从"答案提供者"变为"规则制定者与审阅者"，与 DEC-009"LLM 负责开放语义理解、确定性代码负责校验审计"的架构一致；
- 质量证明从"与金标准一致"转为"结构合同 + 可复现性 + 非语义因素不变性 + 人工审阅"，不再宣称语义绝对准确率；
- 适用范围是语义主观性强的开放归并任务；单 JD 抽取层（P0-3）当时仍保留人工冻结基准（`annotation_cases.json`，approved_frozen），**该保留已被 DEC-015 取消**：抽取层同样改为合同 + 规则场景变形测试 + 稳定性 + 人工违规审计，旧基准降级为 legacy 历史材料。

### 结果与证据

用户 2026-08-03 裁决采纳；`docs/work/P0-4.md` 验收标准已重构；旧夹具及其依赖（CLI 评测命令、预检脚本、13 实例门槛）已删除。

### 复审条件

若市场分析阶段（P0-6/P0-10）发现归并质量不可信、或人工抽样审计成本过高，重新引入小规模人工基准或按关系类型分层评测。

## DEC-013：关系模型收缩为 broader_than 并删除来源不明的旧评测夹具

### 问题

旧关系模型有 `is_a`、`part_of`、`related_to` 三种类型：`related_to` 鼓励"并列即相关"导致关系图过度生成（全图 56~102 条边波动，任选组被全连接）；`is_a` 与 `part_of` 在本项目下游行为完全相同（不归并、报告层级组织、不改变高频计数）却要模型区分；评测依赖的 `data/consolidation_cases.json` 来源和审核过程无法确认。实例归并（P0-4A）与标准项层级（P0-4B）此前共用一套门槛，关系质量卡住实例归并验收。

### 候选方案

- 保留三类型 + 人工 Gold 门槛（无法收敛）；
- 收缩关系模型但保留旧枚举兼容读取（长期保留无业务价值的旧类型）；
- 删除旧夹具、收缩关系模型、4A/4B 分离验收（当前方案）。

### 决策

1. 正式关系只保留 `broader_than`（方向固定 broader -> narrower），统一吸收 `is_a`、`part_of`、上下位、整体/组成；`equivalent` 由多个实例映射到同一 canonical requirement 表达，不保存标准项之间的边；`none` 不持久化；`uncertain` 是模型判断状态，不创建正式边，只进诊断/审计。
2. `related_to` 删除：普通相关性对 P0-6 统计没有明确价值，且容易导致关系图全连接。
3. 旧枚举值从代码中删除；`requirement_relations` 是可再生的实验产物表，删除重建（旧关系数据不保留兼容），批次主记录与 `raw_response` 审计输出保留。
4. `data/consolidation_cases.json` 删除，相关 CLI/脚本/门槛/表述全部移除；只记录"来源和审核过程无法确认，因此不再作为项目资产和验收依据"。
5. P0-4A（实例归并，P0-6 硬依赖）与 P0-4B（标准项层级，增强能力）在合同、评测和状态管理中分离：P0-4B 失败只标记 `hierarchy_status=failed`，不阻塞 P0-4A 落库与 P0-6 统计。

### 主要取舍

- 放弃精细知识图谱：所有包含类关系下游行为相同，统一处理降低模型负担与图失控风险；
- 放弃语义绝对准确率证明：改为合同、稳定性、变形测试、稀疏度与下游不变性控制风险；
- 历史批次关系数据不可恢复（可再生产物）；对无业务价值的旧关系类型不做长期兼容。

### 结果与证据

Prompt 2.1 → 4.0（保守归并、全 mapped、singleton 回退），Schema 1.0 → 2.0；P0-4A 每个实例恰好 mapped 一次（废弃 `unmapped`/`review_required` 正常业务状态）；新增 `app/consolidation_validation.py`（合同、co-clustering、edge Jaccard、统计投影、验收报告）与变形/下游不变性测试；当时全量 135 项测试与 Ruff 通过（`docs/work/P0-4.md`）。

### 复审条件

若报告组织需要更细的关系语义（如区分"是类型"与"是组成部分"），在 P0-4B 上按新验收体系增量扩展关系类型，不得重新引入未分级验收的关系。

# 重大问题复盘

## CASE-001：两段式抽取为何产生

### 现象

Prompt V2.1 按动作和业务环节拆分，职责召回较高但产生过度碎片化；V2.2 强调端到端整体保留后，诊断 Precision 提高而 Recall 明显下降，出现把多个独立交付合并成长职责的问题。

### 影响

职责粒度在过拆与过合之间摆动，人工标准答案与模型输出粒度不一致，直接动摇下游归并与统计。

### 根因

单阶段 Prompt 同时承担“发现原文候选”和“按规则判断结构”两个任务，发现规则与结构规则互相干扰；“多动词就拆”和“同一句就合并”都只是表面启发。

### 尝试过的方案

- V2.1 按动作拆分（过拆）；
- V2.2 端到端整体保留（过合）。

### 最终解决

采用两段式：发现段只定位可能的职责、要求及证据；判断段依据领域无关规则决定拆分、合并、类型、重要程度、熟练度和任选逻辑；确定性代码负责中间合同、完整覆盖、唯一覆盖、证据和最终 Schema 校验（`app/extraction_two_stage.py`，v0.6）。

### 结果

v0.6 开发集/回归集候选门槛达成；验证集第 1 次独立验收端到端原子要求 F1 96.30% 达标（`docs/work/P0-3.md`）。

### 经验

把“发现”与“判断”分离、用中间合同约束、让确定性代码承担覆盖与证据审计，比继续追加 Prompt 规则更可收敛。

## CASE-002：完整归并 JSON 输出截断

### 现象

P0-4 把约 149 条要求实例放入一次完整模型请求，连续 3 次正式验收均未生成可评测批次，最后一次为约 50KB 的 JSON 截断（`Extra data ... char 45135`）。真实模型单次映射请求超过 20 实例时输出可达 15KB 以上。

### 影响

正式归并批次无法形成，P0-4 不能作为 P0-6 稳定输入，付费调用连续失败。

### 根因

单次大响应受模型输出长度限制；只对同一完整请求做有限重试无法绕过截断。

### 尝试过的方案

- 增加重试次数（无效）；
- 继续堆叠单体 Prompt 规则（未解决输出长度问题）。

### 最终解决

改为三阶段/受控分块输出边界：标准项生成 → 按 `mapping_chunk_size` 分块映射（149 实例拆为 50+50+49）→ 关系生成；各阶段独立有限重试、映射块块级覆盖校验；内存合成完整结果后统一执行全局校验，通过后一次性持久化，失败不写库。先写失败测试复现截断再实现。

### 结果

截断问题已修复（`tests/test_consolidation_chunking.py` 转绿）；后续验收口径变更为规则合同 + 稳定性 + 人工抽样复核，输出截断已不再是 P0-4 问题（`docs/work/P0-4.md`、DEC-012）。

### 经验

大输出场景应先改变输出边界（分阶段/分块 + 内存合成 + 全局校验），而不是依赖加大超时或重试；失败测试先行能锁定根因。

## CASE-003：开发集、回归集与验证集污染风险

### 现象

最初 5 个验证集职责样例被用于 Prompt V2.2 设计调试；验证集草稿基线要求名称代理 F1 仅 66.67%，与冻结后正式验收 96.30% 差距巨大。

### 影响

数据一旦参与调参就不再是“未见”数据，用它报告泛化结果会高估或误导；草案基线一度被当作正式验证证据。

### 根因

数据集用途没有在参与调参时及时转组；验证集标注草稿与正式标注口径存在分歧，未经用户裁决就冻结。

### 尝试过的方案

- 直接把验证集草案结果当正式指标（错误，已纠正）；
- 按模型表现挑选验证样例（拒绝）。

### 最终解决

规则固定：用于调参的样例转开发/回归集；验证集按预先确定的规则选择（如“每份现有 JD 的第一条实质职责”），经人工批准冻结（`split_status=approved_frozen`，10 条样例 case_016~025）；草案结果明确标记过期，不作为正式验收证据；据验证集错误调参后该批数据不再承担下一轮正式验证职责。

### 结果

第 1 次独立正式验收在冻结标注上运行，validation 端到端 F1 96.30% 达标；development 门槛复现口径仍在裁决（`docs/work/P0-3.md`）。

### 经验

数据集用途必须随调参行为显式转组；验证集要按规则选取、人工批准冻结、独立运行并如实记录失败案例，草案与正式证据严格分离。

## CASE-004：输入身份不完整导致旧结果误复用

### 现象

归并批次只按范围键和归并器版本判断幂等：新增 JD、重抽取或要求内容变化后，`all` 范围再次运行会错误跳过并继续使用旧批次；按每份 JD 最大抽取记录 ID 装配还可能混用不同抽取器版本。

### 影响

下游统计可能建立在过期或混合版本的归并结果上，结论不可复现。

### 根因

归并结果同时依赖归并规则和实际输入，而输入版本没有进入批次身份。

### 尝试过的方案

- 只按范围键 + 归并器版本幂等（不足）；
- 按最大抽取记录 ID 装配（会混版本）。

### 最终解决

显式冻结选定 JD、共同抽取器版本、抽取记录和完整要求实例，计算 SHA-256 归并输入指纹；批次身份 = 范围键 + 归并器版本 + 输入指纹；目标 JD 缺少目标抽取版本时整体失败（DEC-010）。

### 结果

P0-4 输入装配与批次身份合同全部通过测试，旧批次保留隔离指纹（`docs/work/P0-4.md`）。

### 经验

凡是“结果依赖输入内容”的缓存/幂等，身份必须绑定完整输入版本；不能用范围键或最新记录代替。

## CASE-005：SQLite 外键未启用导致孤立记录风险

### 现象

SQLite 默认不强制外键约束，删除或重建数据时可能出现指向不存在 JD 的孤立抽取/归并记录；旧库重建唯一约束时曾出现外键一致性风险。

### 影响

证据追溯（P0-7）和统计（P0-6）可能引用不存在的来源记录，数据完整性不可信。

### 根因

SQLite 需要连接级 `PRAGMA foreign_keys=ON` 才会执行外键约束；迁移重建唯一约束时若顺序不当会破坏引用。

### 尝试过的方案

- 只在建表时定义外键（默认不生效）；
- 直接重建唯一约束（存在外键风险）。

### 最终解决

数据库初始化开启外键 pragma；迁移时保留数据地重建唯一约束，并在迁移前后检查外键一致性；数据库副本重复初始化后保留历史批次与隔离指纹、外键开启且 0 违规。

### 结果

外键与迁移测试全部通过（`tests/test_database.py`、`tests/test_consolidation_persist.py`）。

### 经验

SQLite 的“定义了外键”不等于“启用了外键”，必须显式开启并在迁移前后验证引用完整性。

## CASE-006：私有实验材料进入 Git 历史

### 现象

P0-3 验证样例生成脚本（`generate_validation_cases.py`）内嵌了真实验证句子、预期标注和判断说明；该脚本曾被提交进 Git 历史。受跟踪文件扫描发现 46 个私有中文字符串指纹，命中路径数为 0（当前版本），但历史 commit 仍包含样例与标注。

### 影响

真实验证材料可能随公开仓库泄露；模型原始响应、人工标准答案和真实 JD 属于禁止提交内容。

### 根因

实验脚本开发时直接复制私有材料到代码文件，缺少“受跟踪代码不得内嵌私有数据”的边界规则。

### 尝试过的方案

- 提交普通删除 commit（只能修正当前版本，不能清除历史）；
- 历史改写与强制推送（用户评估后拒绝）。

### 最终解决

当前版本删除问题脚本；补充防复发规则（受跟踪实验脚本不得内嵌真实 JD 句子、人工标准答案、判断说明或原始响应，需要时从 `data/private/` 读取并脱敏输出）；用不可见指纹扫描确认当前受跟踪文件命中数 0；用户明确接受旧历史保留本次低敏感度实验材料的残余风险（不含凭据、个人隐私或客户机密），不执行历史改写。

### 结果

当前版本已闭环：删除 + 防复发规则 + 指纹审计 + 风险接受记录（`docs/work/P0-3.md`）。

### 经验

私有材料进入受跟踪文件后，普通删除只能遏制当前暴露；必须同时补规则防复发、做范围审计，并把“可接受残余风险”与“不可接受暴露”（凭据、隐私、机密）明确区分，历史清理决策由用户作出。

## DEC-014：两段式 v0.6 经 3 次独立验收批准替换 V2.3.1 成为正式抽取版本

### 问题

P0-2 正式版本 Prompt V2.3.1 在单次完整调用中同时承担全局扫描与局部粒度判断，
P0-3 开发期反复出现职责过拆/欠拆、非穷举示例与任选关系误判；两段式候选 v0.6
把"发现原文候选"与"按规则判断结构"分离（CASE-001），开发集/回归集达到候选门槛，
但 temperature=0 下模型输出仍存在可实测波动，单次运行无法稳定复现冻结门槛。

### 候选方案

- 以 validation 单次运行达标即批准：证据最弱，无法回答波动影响。
- 多次运行统计口径：3 次独立验收运行，validation 每次均须达标，development 取中位数对照门槛。
- 字面门槛继续跑更多轮：波动已实测，可能长期无法通过。

### 决策

用户裁决采用多次运行统计口径并批准替换：3 次独立验收运行中 validation 端到端
原子要求 F1 全部 ≥70%（96.30% / 71.43% / 96.00%），0 最终失败、证据存在率全通过；
development 中位数 2 项未达冻结门槛（要求 F1 95.45% vs 100%、category 85.71% vs 90.91%），
按已定口径不作为否决理由。正式抽取版本由 Prompt V2.3.1 切换为两段式 v0.6
（app/extraction.py 的 PROMPT_VERSION 与 app/extraction_two_stage.py 的
TWO_STAGE_PROMPT_VERSION 均为 "0.6"，测试锁定一致）。

### 主要取舍

- 版本可追溯不变：extractor_version = model|prompt:0.6|schema:2.0 成为新幂等键，
  V2.3.1 历史结果保留；SYSTEM_PROMPT 保留为历史版本供实验对比。
- 接受已知限制：jd_003 的 case_020/021（端到端交付边界、上位单条列举）3 次运行
  全部失败，列入回归关注点，不阻塞本次替换。
- 接受波动风险：validation run2 的 71.43% 仅刚过线，未来迭代仍需独立运行计次。

### 结果与证据

`reports/P0-3/validation-acceptance.md`（本地私有）：3 次独立验收运行汇总、
分层指标与失败案例；代码替换提交 1ab4bd0（app/extraction.py 转发两段式、
测试同步更新，当时全量 135 项测试与 Ruff 通过）。

### 复审条件

v0.7 或后续迭代若针对开发集/验证集错误修改判断段 Prompt，该批数据转开发/回归集，
另建未见样例重新独立验收；验收口径变更须用户裁决。

## DEC-015：抽取层取消完整人工 Gold，改为数据合同 + 规则化验证 + 人工违规审计

### 问题

P0-1 以来，抽取层把少量人工完整标注（`annotation_cases.json` 的 development/
regression/validation 分组）作为正式验收的唯一语义真值：以人工答案 F1、期望
数量一致性和字段准确率作为 Prompt 替换门槛，并据验证集失败案例修改 Prompt。
这套协议存在三个无法回避的问题：

1. 少量 Gold（当前 25 条困难样例）覆盖的表达形态和领域面极窄，无法证明跨表达
   或跨领域泛化；通过它只能说明"与这几十条标注一致"，不能说明抽取规则本身
   合理、稳定或可推广。
2. 每次验收失败都对照人工答案修改 Prompt，等于把人工答案逐轮注入模型行为，
   形成隐藏训练信号（数据集污染风险的规模化版本，见 CASE-003）；样本越少，
   过拟合越容易被误读为"指标提升"。
3. 温度 0 下模型输出仍存在可实测波动（DEC-014），单次对照 Gold 的 F1 本身
   就不稳定，把它当作 Prompt 质量的精确度量会得到虚假精度。

### 候选方案

- 保留人工完整 Gold 作为唯一标准答案，继续按 F1 迭代（无法收敛，且污染风险不可控）。
- 停止人工完整答案作为唯一真值，改为：人类定义数据合同、语义规则、合法判断
  空间、风险边界和审计方法；LLM 按规则对具体 JD 自主判断；确定性代码负责
  Schema、覆盖、证据、唯一性、版本、重试和持久化；人工只做规则制定与违规
  审计（当前方案）。

### 决策

1. 不再以人工完整 JSON 答案、期望数量或字段准确率作为正式 Prompt 验收门槛；
   不得因为模型输出与某个人工答案不同就修改 Prompt。
2. 人类职责转为：定义与维护规则（`docs/annotation/`，规则带稳定 ID）、检查
   规则是否合理、审计模型输出是否违反规则、检查证据支持性、记录风险类型与
   严重度，并决定应修改规则、Prompt、代码还是接受合理差异。
3. 正式质量证明迁移到：数据合同与证据约束（hard gate）+ 多次运行稳定性 +
   规则场景变形测试 + 人工违规审计；多次运行 agreement 只作 warning 基线，
   不预设阈值、不用稳定性冒充准确性。
4. 没有唯一 Gold 不等于任何输出都合法：合同违规、无依据事实、遗漏、重复、
   非法逻辑组、明显不稳定和下游破坏仍然必须被发现。
5. 旧人工标注、F1 报告和 v0.6 审批历史全部保留，但降级为 legacy protocol
   历史材料：命令可复现历史结果，CLI 帮助与文档明确其不属于当前正式验收、
   不得用于批准新的 Prompt，只用于历史比较和案例分析。
6. 仅在"规则本身需要小规模人工参考校准"或"人工审计发现某类表达持续异常、
   需要冻结一组已知行为做回归对照"时，经用户裁决重新引入小规模人工参考，
   且该参考必须明确标注用途与失效条件，不自动恢复为验收门槛。

### 主要取舍

- 放弃"与人工答案的语义准确率"这一可解释数字，换取不被隐藏信号污染、可追溯、
  可重复的规则符合性验证；诚实报告"规则符合性已验证、语义准确率未宣称"。
- 与 DEC-012/013 的关系：P0-4 归并层已先移除了人工金标准（合同 + 稳定性 +
  变形测试 + 下游不变性），本决策把同一原则扩展到抽取层（P0-1/P0-3），并保留
  P0-4 已确立的 hard gate / warning / diagnostic 分级验收结构。
- 本决策只改变评测与治理方法，不取消数据合同、证据连续性、禁止推断、唯一覆盖
  等既有约束；抽取 Schema 与 category 枚举不变。
- 稳定性验证的是"可重复"，不是"正确"；两者分开报告，不得互相替代。

### 结果与证据

P0-1/P0-3 按新协议重开（PARTIAL）；`app/extraction_validation.py` 提供
确定性合同检查、运行间比较与验收报告；`data/rule_scenarios/` 保存领域中性的
规则场景与变形测试；`scripts/experiments/p0_3/run_acceptance.py` 生成分级
验收报告，默认不调用付费模型；两段式 v0.7 Prompt 引用规则 ID 并删除案例式
补丁，v0.6 保留为历史版本。

### 复审条件

当人工审计积累的证据表明某类规则无法用确定性检查覆盖、或需要冻结一组已知
行为时，按决策第 6 条经用户裁决引入小规模人工参考；验收口径变更须用户裁决。
