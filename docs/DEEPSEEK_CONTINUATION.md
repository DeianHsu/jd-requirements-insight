## 3. Codex 对 DeepSeek 原实现的审计补充

### 3.1 P0-4 大问题与修复

| 发现 | 风险判断与原因 | 已完成的设计改进 | 代码与验证入口 |
|---|---|---|---|
| 归并幂等只使用范围键和归并器版本 | 致命数据正确性问题：新增JD、重抽取或要求变化后会静默复用旧批次 | 冻结选定JD、共同抽取器版本、抽取记录和完整要求实例，计算SHA-256归并输入指纹；批次身份改为范围键+归并器版本+输入指纹 | `app/consolidation.py`、`app/models.py`、`app/database.py`；`tests/test_consolidation.py`、`tests/test_consolidation_persist.py`、`tests/test_database.py` |
| 选定范围会静默漏掉没有抽取结果的JD，CLI默认范围含糊 | 致命完整性问题：所谓“全量”实际可能是部分语料池 | CLI必须显式选择 `--all` 或 `--job-id`；目标JD缺少共同抽取器版本时整体失败，不产生部分批次 | `app/cli.py`、`app/consolidation.py`；`tests/test_cli.py`、`tests/test_consolidation.py` |
| SQLite没有持续启用外键 | 高风险持久化问题：孤立映射和关系可进入数据库 | 每个SQLite连接启用外键；旧表保留数据迁移并验证历史批次 | `app/database.py`；`tests/test_database.py` |
| 旧“关系准确率”只检查期望关系命中，未惩罚假阳性 | 高风险验收口径问题：关系全连接也可能获得高分 | 改为在完整标注子图上计算关系 Precision、Recall、F1，并明确统计假阳性 | `app/consolidation_evaluation.py`、`app/cli.py`；`tests/test_consolidation_evaluation.py` |
| 同一标准项对可同时输出多种关系，有向关系可成环 | 大型合同问题：下游统计语义冲突 | 关系类型互斥；`is_a`、`part_of`有向无环；错误反馈包含冲突ID、关系类型或环路原因 | `app/requirement_consolidation.py`；`tests/test_requirement_consolidation.py` |
| 全量失败不可观测且SDK隐式重试干扰计数 | 大型验收流程问题：失败原因和正式次数不可信 | 输出 `summary.errors`；关闭SDK隐式重试；项目层有限重试；连接/读取超时显式配置，读取上限15分钟 | `app/consolidation.py`；`tests/test_consolidation_client.py`、`tests/test_consolidation_run.py` |
| 评测会隐式依赖临时脚本或“最新批次” | 可复现性问题 | 增加正式 `evaluate-consolidation` CLI，要求显式批次ID，纯离线且不调用LLM | `app/consolidation_evaluation.py`、`app/cli.py`；`tests/test_cli.py` |

这些修改的核心原则是：LLM负责开放语义判断，确定性代码负责身份、完整性、合同、冲突、持久化和评测。不得为了让模型输出“通过”而放松这些确定性边界。

### 3.2 P0-3 实验合同问题与修复

DeepSeek 的两段式发现/判断实验方向本身有价值，但发现段覆盖校验曾存在以下问题：

- 同一个分句可被多个候选块重复认领；
- 负索引可能通过并被Python解释为倒序索引；
- `sentence_indexes` 可以非连续或重复；
- `source_span` 只需在全文出现，未证明它准确对应声明的分句索引；
- 候选块ID可重复，影响错误定位与后续引用。

Codex 已在 `app/extraction_two_stage.py` 中补齐块ID唯一、索引非负/有序/连续、每个分句恰好覆盖一次、原文片段与声明索引一致等确定性校验，并在 `tests/test_extraction_two_stage.py` 中覆盖失败路径。该模块仍是实验模块，不得直接接入正式抽取。

历史 v0.1～v0.5 指标是修复前实验产生的阶段记录；修复后只做了自动化测试，没有重新执行付费模型回归。恢复实验时应先做一个小规模可复现检查，不能把历史指标当成修复后代码已经重新验收的证明。

## 5. 建议的后续规划

### 5.1 共同前置步骤

1. 只读恢复上下文并报告文档/代码差异。
2. 运行现有自动化测试和Ruff，建立接手基线；失败时先判断是否为既有工作树问题。
3. 把每次工作限制为一个可独立验证的小目标；完成后立即同步对应handoff。
4. 任何Prompt或架构改动都先静态检查，再小规模验证；小规模通过后才能请求全量正式验收。

### 5.2 P0-4 推荐恢复顺序

优先解决“单次完整输出过大”，不要继续向同一个大Prompt追加规则。推荐先比较并记录以下方案，尚未形成新技术决策前不得把其中任一项写成稳定事实：

1. **优先候选：把映射与关系生成拆成两个阶段。** 第一阶段只产生标准要求项和完整映射，第二阶段只对已确定的标准要求项生成必要关系；最后一次性通过合同后持久化。这样直接缩小单次响应，并隔离关系过度生成。
2. **映射仍会截断时：分批提出候选标准项，再执行全局归并。** 分片只能减少模型上下文，不得牺牲跨片同义合并；最终映射必须覆盖全部实例，且持久化仍是原子操作。
3. **服务端更长完整输出。** 可作为对照或短期验证，不应成为唯一保障，因为它不能解决关系过度生成和全局合同问题。

建议拆成以下小操作：

1. 先写失败可复现测试和新阶段接口测试，不调用模型。
2. 实现“映射结果”和“关系结果”在内存中的组合校验；未全部通过时不写数据库。
3. 保留输入指纹、共同抽取器版本、全局唯一名称、关系互斥/无环和完整覆盖合同。
4. 定向测试通过后跑全量自动化测试和Ruff。
5. 经用户确认后只做JD 1、2的小规模真实预检；关注响应大小、75/75覆盖、关系数量和既有10实例/关系指标。
6. 小规模达标后再请求一次149实例正式验收；在handoff记录新恢复周期的次数、版本、范围、指标和错误。

### 5.3 P0-3 推荐恢复顺序

1. 保持 V2.3.1 为正式抽取基线，两段式 v0.5继续留在实验路径。
2. 先用修复后的覆盖校验做单份JD小规模复现，确认中间合同没有新增失败。
3. 最多做1～2轮“判断段要求侧”规则补齐，重点是原子化、任选关系、类别和熟练度；不要同时重写职责侧规则。
4. 开发集/回归集达到预先固定的候选门槛后，再与P0-5建立并冻结未见验证集；看到验证集结果后不得继续用同一批数据调参并仍称其为验证集。
5. 只有两段式同时保住要求侧基线和职责侧增益，且新验证集达标，才评审是否接入正式抽取。否则保留实验结论，不替换 V2.3.1。
