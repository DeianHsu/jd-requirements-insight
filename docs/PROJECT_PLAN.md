# JD Skill Insight｜项目路线图

> 核心目标：完成一个可评测、可追溯、可演示的JD岗位市场要求分析系统，证明能够把LLM放进真实业务流程并产出可靠结果。

## 一、项目定位与范围

短期只建设以下核心闭环，不同时扩展招聘产品、个人匹配系统和完整Agent系统：

```text
15～20份真实JD
  → 抽取数据合同约束的结构化抽取
  → 复合要求原子化
  → 跨JD原子要求归并与映射
  → 高频要求统计
  → 统计结论追溯原始证据
  → 分层评测与错误分析
  → Markdown市场分析报告
```

项目定位：

> 面向AI应用工程、LLM应用开发和Agent工程岗位的可信市场要求分析系统。

项目重点不是“做一个招聘系统”，而是证明：

> 能够识别LLM在信息抽取中的粒度、分类、证据和评测问题，并用工程方法把非结构化文本转化为可验证、可统计的数据。

简历匹配分、LangGraph、Tool Calling、RAG问答、FastAPI业务接口和前端页面不属于P0核心闭环。

### 目标岗位

- LLM应用开发工程师；
- AI应用开发工程师；
- 初级或转型方向的AI Agent开发工程师；
- RAG应用工程师。

### 目标公司

- 已经拥有真实产品和客户的小型创业公司，而不是只有愿景和口号的团队；
- 有一定规模、研发流程和业务积累的中型公司；
- 主动规避大厂，以及经营多年但仍采用小作坊式管理的小公司。

## 二、功能优先级

功能清单、权重等级（S级核心可信度、A级业务价值、B级呈现与工程底线）和验收标准以第四节P0状态表为唯一信息源；S级和A级功能的设计关切与范围控制已并入对应P0行的验收标准或说明列，本节不重复维护。

测试属于完成门槛。任何S级或A级规则缺少关键测试，都不能标记为完成。

## 三、状态定义

| 状态 | 含义 |
|---|---|
| ✅ 已完成 | 功能代码、必要测试和真实数据验证均达到验收标准 |
| 🟡 部分完成 | 已有稳定实现，但数量、质量或业务闭环尚未达到验收标准 |
| 🟠 开发中 | 只有未提交草稿或正在调整的实现，不能作为稳定事实或下游合同 |
| ⬜ 未开始 | 尚无可验证实现 |
| 🔵 长期范围 | 不属于P0核心闭环，待依赖能力稳定后再评估 |

## 四、P0：短期核心闭环

只有下面的P0功能全部达到各自验收标准，P0核心闭环才算完成。

### 功能硬依赖

硬依赖只表示下游实现必须使用已交付的上游接口、Schema、数据库结构或公共行为。数据流先后、验收样本和完成门禁单独列出，不构成开发阻塞；互不依赖的功能可并行。下游只有在全部硬依赖获得 `APPROVED` 后才能开始开发，且不得在下游任务中修改已验收上游。

| 功能单元 | 功能硬依赖 | 非硬依赖的验收输入或门禁 |
|---|---|---|
| P0-1 | 无 | 无 |
| P0-2 | P0-1 | 无 |
| P0-3 | P0-2 | 无 |
| P0-4 | P0-2 | 可与P0-3并行 |
| P0-5 | P0-3、P0-4 | 无 |
| P0-6 | P0-4 | P0-8提供正式规模的验收数据 |
| P0-7 | P0-2、P0-6 | 无 |
| P0-8 | P0-2 | 为P0-6和P0-10提供验收输入 |
| P0-9 | 无（横向质量功能） | 是P0整体和P0-11的完成门禁 |

## 五、评测分层设计

评测必须分开报告抽取、原子化、要求映射、字段和证据质量，不能用单一总分替代。数据集划分、指标含义和错误复核方式以[annotation/DATASET_EVALUATION.md](annotation/DATASET_EVALUATION.md)为准；本计划只维护验收目标：验证集端到端原子要求F1不低于70%，并如实报告其他分层指标和失败案例。

## 八、P0完成定义

以下清单是第四节P0状态表全部达到✅已完成的汇总检查，条目细节以第四节验收标准为准。P0只有同时满足以下条件才可以标记为完成：

1. 至少15份真实目标岗位JD完成导入和结构化抽取；
2. 抽取数据合同和人工标注规范明确且与代码一致；
3. 复合要求可以原子化，每个要求实例可追溯地映射到标准要求项，并保存关系类型、映射依据和原始证据；
4. 高频统计按独立JD计数，并区分必需、加分和普通提及；
5. 每个统计结论可以追溯到具体JD和原文片段；
6. 8～10份人工标准答案划分开发集和验证集，分层指标及失败案例被真实记录；
7. 核心规则具有确定性测试，全部测试与Ruff检查通过；
8. 可以生成一份真实数据驱动的Markdown市场分析报告；
9. README、架构说明和演示脚本与实现保持一致。
