# JD Skill Insight 文档管理规则

本文规定项目文档的职责、唯一信息源和同步方式，不规定代码实现细节或GitHub公开范围。

## 1. 文档职责与唯一信息源

| 文档 | 唯一职责 |
|---|---|
| `AGENTS.md` | Codex每次开发时必须遵守的行为规则 |
| `docs/CONTEXT_ROUTING.md` | 按任务选择最小必要上下文 |
| `docs/GLOSSARY.md` | 维护全项目通用术语、固定含义、禁止误用和跨阶段语义不变量 |
| `docs/PROJECT_PLAN.md` | 功能范围、权重、顺序、验收标准和实时状态 |
| `docs/DECISIONS.md` | 重要产品与技术选择的背景、理由、影响和复审条件 |
| `docs/handoff/` | 按P0功能点保存持续维护的当前工程交接，入口为`docs/handoff/README.md` |
| `docs/annotation/` | JD标注和数据语义规范，入口为`docs/annotation/README.md` |
| 根目录`README.md` | 面向公开用户说明项目定位、当前能力、环境和使用方法 |
| 功能目录`README.md` | 说明目录内代码文件的职责、实现原理和相互关系 |
| `reports/` | 保存Prompt版本或评测里程碑的阶段实验记录 |
| `docs/PUBLISH_RULES.md` | GitHub公开内容、隐私边界和发布检查 |

同一信息只在职责对应的文档中完整维护。其他文档只保留必要摘要和链接；修改时先更新唯一信息源，再检查相关摘要、链接和公开范围。

项目术语发生新增、重命名、边界调整或同词异义时，先更新`docs/GLOSSARY.md`。设计和实现文档引用术语，不重复维护另一套定义。

## 2. 语言与命名

1. 中文正文使用`docs/GLOSSARY.md`规定的中文标准术语；不要为了与代码同形而堆叠英文业务名词。
2. 类名、字段名、枚举值、文件名和CLI命令保留准确的英文代码标识符，并使用反引号。
3. 同一对象在代码、测试、标题和文档中使用同一词根；新增公共命名前先搜索现有称呼和高频业务术语。
4. “技能”只指具体技术或能力；跨类别数据使用“岗位要求、原子要求、要求实例、标准要求项、要求映射”等准确名称。
5. 术语词典按业务类别和处理顺序组织，不按字典序排序。

## 3. 功能目录README

1. 每个包含功能代码的目录都必须设置`README.md`，测试目录遵守相同规则。
2. 新增、删除或重命名代码文件时，同步更新所在目录的`README.md`。
3. 目录README逐一说明代码文件的职责、核心实现原理以及与其他文件的关系。
4. 为保证独立可读，允许目录README保留必要技术摘要，但不得复制完整计划、标注规范或实验报告。

## 4. 项目计划同步

1. 实现、删除、调整或移出计划功能时，在同一次改动中更新`docs/PROJECT_PLAN.md`的状态、验收说明和实现路径。
2. 功能只有满足计划中已有验收标准后才能标记为“✅ 已完成”；技术骨架或少量样本通过不等于业务验收完成。
3. 计划文档保存当前状态，历史技术取舍写入决策记录，不在多个文档重复维护完整进度。

## 5. 决策记录

1. 只有存在明确替代方案、具有长期影响，并且之后仍需解释理由的选择才写入`docs/DECISIONS.md`。
2. 产品定位、重大范围调整、架构、数据模型、依赖、隐私边界和评测方法通常属于决策；普通任务顺序、实现细节、缺陷修复和每日进度不属于决策。
3. 每条决策至少记录状态、背景、决策、理由、影响和复审条件。
4. 决策变化时保留旧记录并标记“已替代”，新增后续决策并注明替代关系。

## 6. P0功能交接

handoff的职责、命名、读取、依赖、维护、隐私边界和完成检查全部以`docs/handoff/README.md`为唯一规则，本文不重复。

## 7. 阶段报告

Prompt分析报告只在Prompt版本变化、人工标准答案验证集冻结或实验结论发生实质变化时更新。普通抽取、重复评测和中间调试不更新报告。

## 8. 文档一致性检查

纯文档或配置改动检查内容一致性、相对链接、格式、忽略规则和敏感信息。发现重复时保留唯一信息源中的完整内容，其余位置改为摘要与链接。
