# 功能目标与边界

让每个统计结论能够回到对应JD、公司、岗位、重要程度、原始要求名称和连续原文证据。P0-7负责查询和展示追溯链，不负责决定要求是否同义或计算频率。

# 当前状态

部分完成。JD正文、来源元数据、职责和要求的逐条证据已经持久化；P0-4已建立标准要求项到要求实例的映射、外键和批次输入身份，尚缺P0-6统计查询及本功能的报告展示。

# 稳定事实

- P0-2已经保存JD来源、原始正文和逐条连续证据。
- `raw_name`和证据必须保留，不能被P0-4标准名称覆盖。
- 普通运行日志不能替代业务追溯关系，也不得保存JD正文或完整证据。
- 追溯结果必须携带归并批次ID或输入指纹，避免在多个输入版本并存时引用错误映射。

# 实现与文件入口

- `app/models.py`：JD、抽取结果、要求实例及归并批次、标准要求项和要求映射关系。
- `app/extraction.py`：抽取结果持久化。
- `app/database.py`：现有数据库结构。
- `app/consolidation.py`：P0-4批次身份、映射持久化与原始要求外键；P0-6查询尚未建立。

# 数据合同与不变量

- 追溯链必须通过稳定ID连接标准要求项、要求映射、要求实例和JD。
- 展示可以截取必要信息，但业务数据层必须保留完整连续证据。
- 不在日志、公开文档或终端错误摘要中泄露真实JD正文和完整证据。

# 测试与验证

全量110项测试和Ruff通过；现有测试覆盖JD、职责、要求、归并映射外键、历史批次迁移和指定归并批次加载，但没有统计结论到证据的端到端查询测试。

- 尚缺证据查询接口、分页或摘要策略及报告展示。
