# 架构与功能依赖规则

本文规定 P0 功能单元、功能依赖、上下游修改和长期架构边界。具体产品取舍及其历史理由以 `docs/DECISIONS.md` 为准。

## 1. P0 功能单元

1. `docs/PROJECT_PLAN.md` 中的 `P0-X` 是当前最小规划、开发和验收单元，不再拆分任务编号。
2. 一个 P0 可以经历多轮迭代，但始终复用同一组 Design、Develop、Review；历史由 Git 保存。
3. 只有 P0 大到无法形成单一可验收边界时，才由 Tech Lead 重新评估是否拆分，不提前设计子任务体系。

## 2. 关系类型

- **功能硬依赖**：下游实现需要调用、导入、查询或依赖上游已经稳定的接口、Schema、数据库结构或公共行为。权威关系维护在 `docs/PROJECT_PLAN.md`。
- **验收输入**：只影响最终业务验收，不阻塞独立实现，例如真实数据规模、正式批次或未见验证集。
- **普通数据流**：只描述数据经过哪些阶段，不自动构成功能开发依赖。

硬依赖未通过 Review 时，Tech Lead 可以提前设计下游，Developer 不得实施下游业务代码。没有硬依赖路径的 P0 可以平行开发。

## 3. 上游保护

1. 下游 Developer 不得直接修改已验收上游的接口、Schema、数据语义或公共行为。
2. 下游发现上游问题时，在当前 Develop 提交指向目标 P0 的 Change Request。
3. Tech Lead 决定是否重新打开上游；只有实际受影响的下游暂停。
4. 上游重新 `APPROVED` 后，Tech Lead 根据 Git 差异决定下游是否需要重做或重新验收。
5. 共享文件不等于共享功能所有权；修改前按行为归属判断对应 P0，并保护其他平行开发改动。

## 4. 当前产品与技术边界

1. P0 核心是可信岗位要求数据闭环，不扩展为完整招聘系统、简历匹配打分器或自动投递 Agent。
2. SQL 负责精确统计；RAG 延后用于开放式证据检索。
3. 当前正式入口以 CLI 和 Markdown 报告为主，不为展示框架而引入 Agent 编排、复杂前端或完整业务 API。
4. LLM 负责开放语义理解；确定性代码负责数据合同、身份、完整性、冲突、持久化和评测。
5. 业务合同、可复用解析、查询和评测逻辑进入 `app/`并配套测试；实验脚本不得成为未声明的正式入口。

## 5. Change Request

Change Request 保存在当前 Develop，不建立第四类任务文档。状态只使用 `OPEN`、`ACCEPTED`、`DECLINED`或 `SUPERSEDED`；当前文件只保留尚未解决或仍影响实现的请求，历史处理过程由 Git 保存。Tech Lead 接受后必须先更新 Design，Developer 再按新设计实施。
