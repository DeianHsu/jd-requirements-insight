# 测试与验证规则

本文规定代码、Prompt、数据合同和文档变更的验证顺序、角色责任与完成边界。测试和实验由Developer执行；Tech Lead只审查证据。

## 1. 验证顺序

Developer按“静态检查 → 小规模验证 → 全量回归 → 版本确认”推进，前一阶段失败不得进入下一阶段。

1. **静态检查**：语法、类型、抽取数据合同、数据库结构、接口、确定性规则、相关自动化测试和 Ruff；不调用付费服务。
2. **小规模验证**：只使用覆盖本次变化的少量测试、困难样例或数据；Prompt和业务语义使用少量真实样例。
3. **全量回归**：小规模通过后，按影响范围运行完整测试和必要真实数据回归；昂贵全量LLM调用只在此阶段并按实验规则授权。
4. **版本确认**：Developer提交达到 Design 和`PROJECT_PLAN.md`既有验收标准的完整证据后，Tech Lead才能通过Review确认版本或标记完成。

## 2. 角色边界

### Developer

- 设计与编写测试，执行目标测试、完整测试、静态检查、离线评测和经授权的模型实验。
- 确认测试对象与`implementation_revision`一致，并在Develop记录实际命令、环境、数据范围、结果、警告和详细报告路径。
- Review要求补充证据时，由Developer补测试、重跑或解释；不得让Tech Lead代为完成。

### Tech Lead

- 读取Design、Develop、测试/实验报告和Git差异，必要时检查业务代码与测试源码是否覆盖目标行为。
- 不运行静态检查、自动化测试、离线评测、小规模复现或模型实验。
- 只判断证据是否真实、充分且与当前revision一致；证据不足时给出`CHANGES_REQUESTED`，不得自行运行测试后代替Developer补齐。

## 3. 测试边界

- 自动化测试不得调用有费用的外部服务。
- 测试使用临时文件、虚构数据和临时SQLite数据库，不读取或修改真实JD、完整标注、项目数据库、密钥或私人材料。
- 每个测试验证一个清晰行为；测试数量不是目标，关键失败路径覆盖才是目标。
- 确定性测试负责结构、合同、迁移、冲突和聚合规则；LLM业务语义仍需人工标准答案评测。
- 无适用样本的指标显示`N/A`，不得显示为0%。

## 4. 变更类型

- 功能代码：先目标测试，再按影响范围执行完整测试和Ruff。
- Prompt、LLM或业务语义：除自动化测试外，按预先冻结的样例和指标进行小规模及正式验收。
- 纯文档或配置：只检查内容、链接、格式、忽略规则和敏感信息，不运行无关业务测试。

## 5. 结果记录

Develop只记录Developer实际执行的当前有效命令、环境、范围、实现revision、结果和结论；详细实验过程进入对应P0报告。Review必须把验收结论绑定到明确的Design commit和实现revision，不得用未验证草稿、口头说明或历史其他版本的结果证明当前实现。
