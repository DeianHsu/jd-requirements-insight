# 文档管理规则

本文规定项目文档的唯一职责、当前快照、README、状态同步和一致性检查。

## 1. 唯一信息源

| 文档 | 唯一职责 |
|---|---|
| `AGENTS.md` | 所有Agent始终遵守的最高级原则和一级路由 |
| `docs/roles/` | Tech Lead与Developer的职责、读取顺序和修改权限 |
| `docs/rules/` | 按领域选择性读取的长期Agent规则 |
| `docs/GLOSSARY.md` | 全项目术语、固定含义和跨阶段不变量 |
| `docs/PROJECT_PLAN.md` | P0范围、功能硬依赖、验收输入、顺序、验收标准和实时状态 |
| `docs/DECISIONS.md` | 长期产品与技术决策的背景、理由、影响和复审条件 |
| `docs/design/P0-X.md` | 当前P0应该实现什么 |
| `docs/develop/P0-X.md` | 当前P0实际实现了什么 |
| `docs/review/P0-X.md` | 当前P0实现是否通过验收 |
| `docs/annotation/` | JD标注、证据和评测数据语义规范 |
| `README.md`与目录README | 面向人类的项目说明、目录索引、文件职责和运行方式 |
| `reports/P0-X/` | 对应P0的详细阶段实验分析 |

同一信息只在职责对应的文档完整维护，其他位置保留必要摘要和链接。

## 2. Design、Develop、Review 生命周期

1. 未开始且未规划的P0不创建三类文档。
2. 开始规划时创建Design；进入开发时创建Develop；实际进入验收时创建Review，不提前占位。
3. 已完成或验收失败的P0保留三份当前快照；同一P0多轮迭代始终复用同一文件。
4. 三类文档只描述当前事实，不保留旧方案、旧问题、历次验收轮次、已关闭Change Request或每日流水；历史由Git和实验报告保存。
5. Design由Tech Lead维护，Develop由Developer维护，Review由Tech Lead维护；三类文档对双方均可读。

## 3. 项目状态与决策

1. 实现、删除、调整或移出计划功能时，同步更新`PROJECT_PLAN.md`的状态、验收说明和当前文档入口。
2. 只有Review为`APPROVED`且满足计划中已有验收标准，才能标记P0完成。
3. 技术骨架、少量样本或小规模预检通过不等于业务完成。
4. 只有存在明确替代方案、长期影响且以后仍需解释理由的产品定位、架构、数据模型、依赖、隐私或评测选择才写入`DECISIONS.md`。
5. 决策变化时保留旧记录并标记已替代，新增后续决策；普通实现细节和每日进度不写决策。

## 4. README 面向人类

1. 根README说明项目定位、当前能力、环境、使用方法和人类文档索引。
2. 代码与测试目录README说明目录用途、文件职责、模块关系、数据流和运行方式。
3. README不得承担Agent角色识别、读取顺序、权限、Change Request或强制开发流程；这些内容只进入`AGENTS.md`、角色文档和规则文档。
4. 新增、删除或重命名代码文件时同步更新对应目录README的文件索引。

## 5. 写作与技术说明

- 中文正文使用GLOSSARY规定的标准术语；代码标识符保留准确英文并使用反引号。
- 技术讲解提供项目文件路径；可定位时附关键类、函数或行号。
- 重要技术点列出核心实现和测试入口。
- 未实现的功能明确标注“尚未实现”，不得提供误导性路径。
- 文档不得复制真实JD、完整模型JSON、完整人工标准答案、数据库内容、密钥或私人材料。

## 6. 一致性检查

完成前检查状态、依赖、术语、路径、相对链接、README索引、报告入口、忽略规则和敏感信息。发现重复时保留唯一信息源，其他位置改为摘要与链接。纯文档或配置改动不运行无关业务测试。
