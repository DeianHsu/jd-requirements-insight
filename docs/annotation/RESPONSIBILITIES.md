# 岗位职责标注规范

> 只在标注职责、检查职责原子化或分析职责过度拆分时读取本文。

## 1. 职责边界

职责表示候选人入职后需要完成的工作，不等同于候选人已经具备的技能。

```text
负责企业知识库和RAG系统开发。
```

可以标注为：

```json
{
  "name": "开发企业知识库和RAG系统",
  "evidence": "负责企业知识库和RAG系统开发。"
}
```

职责中出现的技术只有在JD同时明确要求候选人掌握时，才作为`must`或`preferred`要求；只在工作场景出现时最多标为`mentioned`。

## 2. 什么时候拆分

当一句话包含不同对象、不同交付物或可以独立验收的业务结果时拆分。

```text
设计Agent架构、开发核心代码，实现药物研发数据自动化处理。
```

拆为：

1. 设计Agent架构；
2. 开发Agent核心代码；
3. 实现药物研发数据自动化处理。

“搭建RAG系统并优化检索性能”也可以拆为“搭建RAG系统”和“优化检索性能”，因为两项具有不同交付结果。

## 3. 什么时候整体保留

不能见到多个动词就机械拆分：

- 多个动作作用于同一对象，并共同构成一个端到端交付时可以整体保留，例如“设计、开发与落地AI Agent管理平台”；
- 并列内容只是系统能力属性时不拆，例如“构建具备规划、调度、推理与执行能力的基础设施”；
- 技术、模型或产品类型只是示例时不拆，例如“开发企业内部AI应用（Agent、智能助手等）”；
- 拆分后只剩“设计”“开发”“落地”等缺少对象和业务含义的通用动作时，应恢复为完整职责。

## 4. 职责名称

每个名称应包含一个清晰的“动作 + 对象或结果”。允许为可读性调整语序，但不得加入原文没有的业务事实。

合适：

```text
构建智能体工作流
实现文献检索自动化
优化模型效果与推理性能
```

不合适：

```text
负责相关工作
设计
开发与落地及持续优化全部系统
```

## 5. 证据

证据必须是JD中的连续文本，并足以支持职责名称。拆分后的多项职责可以共享同一句证据，但不能拼接不连续片段。

证据通用规则和Golden数据管理见[DATASET_EVALUATION.md](DATASET_EVALUATION.md)。

## 6. 评测关注点

当前validation职责草案专门检查两类错误：

1. 把端到端动作链拆成大量低价值通用动作；
2. 把能力属性或括号中的示例错误拆成独立职责。

validation草案批准后必须冻结；如根据其结果修改Prompt，下一轮正式验证需使用新的未见样例。
