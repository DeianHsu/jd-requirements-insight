# 岗位职责规则（RESP）

> 只在标注职责、检查职责原子化或分析职责过度拆分时读取本文。
> 规则 ID：`RESP-01`～`RESP-07`。修改规则语义必须同步更新本文件、Prompt 引用和测试。

## RESP-01 职责边界

职责表示候选人入职后需要完成的工作，不等同于候选人已经具备的技能。

```text
负责企业知识库和RAG系统开发。
```

可以标注为：

```json
{
  "name": "开发企业知识库和RAG系统",
  "evidence": "负责企业知识库和RAG系统开发。"
}
```

职责中出现的技术只有在 JD 同时明确要求候选人掌握时，才作为 `must` 或 `preferred` 要求；只在工作场景出现时最多标为 `mentioned`。

## RESP-02 拆分

当一句话包含不同对象、不同交付物或可以独立验收的业务结果时拆分。

```text
设计Agent架构、开发核心代码，实现药物研发数据自动化处理。
```

拆为：

1. 设计Agent架构；
2. 开发Agent核心代码；
3. 实现药物研发数据自动化处理。

“搭建RAG系统并优化检索性能”也可以拆为“搭建RAG系统”和“优化检索性能”，因为两项具有不同交付结果。

## RESP-03 合并（端到端交付）

不能见到多个动词就机械拆分：

- 多个动作作用于同一对象，并共同构成一个端到端交付时可以整体保留，例如“设计、开发与落地AI Agent管理平台”；
- 并列内容只是系统能力属性时不拆，例如“构建具备规划、调度、推理与执行能力的基础设施”；
- 技术、模型或产品类型只是示例时不拆，例如“开发企业内部AI应用（Agent、智能助手等）”；
- 拆分后只剩“设计”“开发”“落地”等缺少对象和业务含义的通用动作时，应恢复为完整职责。

## RESP-04 实施方式

协作对象、使用技术和执行手段通常是实施方式，不单独形成职责，但其承载的交付不能丢失。例如“与产品及业务团队协作，构建智能系统基础设施”抽取为“与产品及业务团队协作构建智能系统基础设施”。

## RESP-05 非穷举示例

“如”“例如”“等”和括号中的内容如果只是上位业务对象的示例，不能展开成独立职责。例如“开发企业内部AI应用（Agent、智能助手等）”只抽取“开发企业内部AI应用”，Agent 和智能助手只是示例。

## RESP-06 环节列举概括

以“参与/负责/围绕”+ 同一对象的多个组成部分或环节（如定义、编排、集成、训练、发布、治理，或多个子能力、模块、机制）开头的内容，是同一项研发或建设工作的组成部分，合并为一项概括职责（如“开展XX全生命周期研发”“建设XX体系”），不得拆成多项。环节列举概括只在列举项属于同一对象的组成部分时适用，不能用来合并不同业务对象。

## RESP-07 职责名称

每个名称应包含一个清晰的“动作 + 对象或结果”，只保留动作与核心对象/结果，不保留整句的修饰前缀和列举（修饰语和列举内容保留在 `evidence` 中）。允许为可读性调整语序，但不得加入原文没有的业务事实。

合适：

```text
构建智能体工作流
实现文献检索自动化
优化模型效果与推理性能
```

不合适：

```text
负责相关工作
设计
开发与落地及持续优化全部系统
```

## 证据

证据必须是 JD 中的连续文本，并足以支持职责名称（`EVID-01`、`EVID-02`）。拆分后的多项职责可以共享同一句证据，但不能拼接不连续片段（`EVID-03`）。证据通用规则和验证协议见 [DATASET_EVALUATION.md](DATASET_EVALUATION.md)。

## 人工审计关注点

人工违规审计（非正式验收门槛）重点检查两类错误：

1. 把端到端动作链拆成大量低价值通用动作（违反 `RESP-03`、`RESP-06`）；
2. 把能力属性或括号中的示例错误拆成独立职责（违反 `RESP-05`）。

审计记录使用 `docs/annotation/README.md` 定义的人工审计格式（`rule_id` / `violation` / `severity` / `evidence` / `reason` / `recommended_action`）。
